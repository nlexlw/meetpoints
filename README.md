# RFC 0001: MeetPoint MVP

**Статус:** Draft  
**Версия:** 1.0  
**Проект:** MeetPoint  
**Тип документа:** RFC / техническое описание MVP  
**Назначение:** описание логики, требований и API приложения для нетворкинга на мероприятиях

---

## 1. Введение

### 1.1. Назначение приложения

MeetPoint - это web-сервис для знакомств и нетворкинга на мероприятиях: хакатонах, конференциях, митапах, образовательных программах и форумах.

Главная идея приложения - помочь участникам быстро находить полезные контакты внутри конкретного события. Вместо случайного общения участник получает рекомендации по людям с похожими интересами, тегами и целями.

### 1.2. Проблема

На мероприятиях часто сложно познакомиться с нужными людьми, потому что:

- участники не знают, кто находится рядом;
- нет удобного способа понять интересы других людей;
- не все готовы первыми начинать разговор;
- контакты часто теряются после мероприятия;
- организатору сложно отслеживать активность участников.

### 1.3. Цель MVP

MVP должен проверить базовую гипотезу:

> Если участникам мероприятия дать простой способ находить людей по интересам и обмениваться контактами только при взаимном интересе, то качество нетворкинга на событии повысится.

### 1.4. Основной сценарий

1. Организатор создает мероприятие.
2. Система генерирует ссылку или QR-код для входа.
3. Участник сканирует QR-код.
4. Участник заполняет короткий профиль.
5. Участник видит рекомендованных людей.
6. Участник отправляет запрос на знакомство.
7. Контакты открываются только при взаимном интересе.

## 2. Термины и определения

### 2.1. Event

**Event** - мероприятие, созданное организатором.  
Примеры: хакатон, конференция, воркшоп, митап.

Содержит:

- название;
- описание;
- список доступных тегов;
- статус регистрации;
- список участников.

### 2.2. Participant

**Participant** - участник мероприятия.

Содержит:

- имя;
- краткое описание;
- интересы;
- теги;
- контактные данные;
- принадлежность к конкретному мероприятию.

### 2.3. MeetRequest

**MeetRequest** - запрос на знакомство между двумя участниками.

Состояния:

- `pending` — запрос отправлен;
- `accepted` — запрос принят;
- `rejected` — запрос отклонен или неактивен.

### 2.4. Match

**Match** - ситуация, когда два участника взаимно заинтересованы в знакомстве.

После match система может показать контактные данные участников друг другу.

### 2.5. Tags

**Tags** - интересы или темы, которые помогают системе рекомендовать участников друг другу.

Примеры:

- `Python`;
- `Design`;
- `Startups`;
- `AI`;
- `Product Management`;
- `Frontend`;
- `Backend`;
- `Data Science`.

## 3. Роли пользователей

### 3.1. Организатор

Организатор управляет мероприятием.

Организатор должен иметь возможность:

- создать мероприятие;
- указать название и описание;
- задать теги мероприятия;
- получить ссылку или QR-код;
- просматривать список участников;
- закрыть регистрацию;
- управлять базовыми настройками события.

### 3.2. Участник

Участник использует приложение для поиска полезных знакомств.

Участник должен иметь возможность:

- присоединиться к мероприятию;
- создать короткий профиль;
- выбрать интересы;
- видеть рекомендации;
- отправлять запросы на знакомство;
- принимать запросы;
- видеть контакты только после взаимного согласия.

### 3.3. Система

Система отвечает за:

- хранение данных;
- обработку запросов;
- рекомендации участников;
- проверку прав доступа;
- защиту контактных данных;
- контроль статуса регистрации.

---

## 4. Функциональные требования

### 4.1. Создание мероприятия

Система должна позволять создать мероприятие через API.

Минимальные данные:

- `title`;
- `description`;
- `tags`.

После создания события система должна вернуть:

- `event_id`;
- данные события;
- статус регистрации.

### 4.2. Подключение участника к мероприятию

Участник должен иметь возможность присоединиться к мероприятию по `event_id`.

При регистрации участник указывает:

- имя;
- описание;
- список тегов;
- контактные данные.

Если регистрация закрыта, система должна запретить добавление нового участника.

### 4.3. Рекомендации

Система должна рекомендовать участников внутри одного мероприятия.

Базовый алгоритм MVP:

1. Взять теги текущего участника.
2. Сравнить их с тегами других участников.
3. Посчитать количество совпадений.
4. Отсортировать участников по количеству общих тегов.
5. Вернуть список наиболее релевантных людей.

Участник не должен видеть самого себя в рекомендациях.

### 4.4. Запрос на знакомство

Участник должен иметь возможность отправить запрос другому участнику.

Ограничения:

- нельзя отправить запрос самому себе;
- нельзя отправить дубликат активного запроса;
- нельзя отправить запрос участнику из другого мероприятия.

### 4.5. Принятие запроса

Получатель запроса должен иметь возможность принять запрос.

После принятия запроса система должна:

- изменить статус запроса на `accepted`;
- разрешить участникам видеть контакты друг друга.

### 4.6. Закрытие регистрации

Организатор должен иметь возможность закрыть регистрацию на мероприятие.

После закрытия регистрации:

- новые участники не могут присоединяться;
- уже зарегистрированные участники продолжают пользоваться функциями нетворкинга.

---

## 5. Нефункциональные требования

### 5.1. Простота

MVP должен быть простым и понятным.  
Основной сценарий участника должен занимать не больше нескольких минут.

### 5.2. Скорость работы

API должно быстро отвечать на основные запросы:

- создание события;
- регистрация участника;
- получение рекомендаций;
- отправка запроса;
- принятие запроса.

Для MVP допускается использование SQLite.

### 5.3. Надежность

Система должна корректно обрабатывать ошибки:

- несуществующее мероприятие;
- несуществующий участник;
- закрытая регистрация;
- повторный запрос;
- попытка открыть контакты без match.

### 5.4. Расширяемость

Архитектура должна позволять в будущем добавить:

- авторизацию;
- личные кабинеты;
- QR-коды;
- аналитику для организатора;
- чат;
- push-уведомления;
- экспорт контактов;
- интеграцию с Telegram.

### 5.5. Безопасность

Контакты участников не должны быть доступны всем пользователям.

Контактные данные можно показывать только если:

- запрос на знакомство принят;
- между участниками есть match;
- оба участника принадлежат одному мероприятию.

---

## 6. Архитектура приложения

### 6.1. Backend

Backend реализуется на FastAPI.

Основные задачи backend:

- принимать HTTP-запросы;
- валидировать данные;
- работать с базой данных;
- возвращать JSON-ответы;
- реализовывать бизнес-логику.

### 6.2. Database

Для MVP используется SQLite.

Основные таблицы:

- `events`;
- `participants`;
- `meet_requests`.

### 6.3. ORM

Для работы с базой данных используется SQLAlchemy.

ORM позволяет:

- описывать таблицы как Python-классы;
- выполнять запросы к базе;
- связывать сущности между собой.

### 6.4. Schemas

Для валидации входных и выходных данных используется Pydantic.

Pydantic-схемы должны разделять:

- данные для создания;
- данные для обновления;
- данные для ответа клиенту.

### 6.5. Frontend

Frontend в MVP может быть простым web-интерфейсом.

Минимальные экраны:

- главная страница;
- создание мероприятия;
- подключение участника;
- профиль участника;
- список рекомендаций;
- список запросов;
- экран match.

## 7. API Specification

### 7.1. Service endpoints

#### `GET /`

Проверка, что сервер работает.

Пример ответа:

```json
{
  "message": "MeetPoint API is running"
}
```

#### `GET /health`

Проверка состояния сервиса.

Пример ответа:

```json
{
  "status": "ok"
}
```

---

### 7.2. Events

#### `POST /events`

Создает новое мероприятие.

Пример тела запроса:

```json
{
  "title": "PROD Hackathon Minsk",
  "description": "Hackathon for students and young developers",
  "tags": ["Python", "Startups", "AI", "Design"]
}
```

Пример ответа:

```json
{
  "id": 1,
  "title": "PROD Hackathon Minsk",
  "description": "Hackathon for students and young developers",
  "tags": ["Python", "Startups", "AI", "Design"],
  "is_registration_open": true
}
```

#### `GET /events/{event_id}`

Возвращает информацию о мероприятии.

#### `PATCH /events/{event_id}/close`

Закрывает регистрацию на мероприятие.

Пример ответа:

```json
{
  "id": 1,
  "is_registration_open": false
}
```

---

### 7.3. Participants

#### `POST /events/{event_id}/participants`

Регистрирует участника на мероприятие.

Пример тела запроса:

```json
{
  "name": "Nelli",
  "bio": "Python developer interested in AI and product analytics",
  "tags": ["Python", "AI", "Backend"],
  "contact": "@nlexlw"
}
```

Пример ответа:

```json
{
  "id": 1,
  "event_id": 1,
  "name": "Nelli",
  "bio": "Python developer interested in AI and product analytics",
  "tags": ["Python", "AI", "Backend"]
}
```

#### `GET /events/{event_id}/participants`

Возвращает список участников мероприятия.

#### `GET /participants/{participant_id}`

Возвращает публичный профиль участника.

Контактные данные не должны возвращаться без match.

---

### 7.4. Recommendations

#### `GET /participants/{participant_id}/recommendations`

Возвращает рекомендованных участников.

Пример ответа:

```json
[
  {
    "id": 2,
    "name": "Alex",
    "bio": "Frontend developer and designer",
    "tags": ["Design", "Frontend", "Startups"],
    "shared_tags": ["Startups"],
    "score": 1
  }
]
```

---

### 7.5. Meet Requests

#### `POST /meet-requests`

Создает запрос на знакомство.

Пример тела запроса:

```json
{
  "from_participant_id": 1,
  "to_participant_id": 2
}
```

Пример ответа:

```json
{
  "id": 1,
  "from_participant_id": 1,
  "to_participant_id": 2,
  "status": "pending"
}
```

#### `PATCH /meet-requests/{request_id}/accept`

Принимает запрос на знакомство.

Пример ответа:

```json
{
  "id": 1,
  "status": "accepted"
}
```

#### `GET /participants/{participant_id}/matches`

Возвращает список взаимных знакомств.

Контакты можно вернуть только для участников, у которых есть принятый запрос.

## 8. Data Model

### 8.1. Event

```python
class Event:
    id: int
    title: str
    description: str
    tags: list[str]
    is_registration_open: bool
```

### 8.2. Participant

```python
class Participant:
    id: int
    event_id: int
    name: str
    bio: str
    tags: list[str]
    contact: str
```

### 8.3. MeetRequest

```python
class MeetRequest:
    id: int
    from_participant_id: int
    to_participant_id: int
    status: str
```

### 8.4. Связи между сущностями

- Один `Event` содержит много `Participant`.
- Один `Participant` принадлежит одному `Event`.
- Один `Participant` может отправить много `MeetRequest`.
- Один `Participant` может получить много `MeetRequest`.
- `MeetRequest` связывает двух участников.

---

## 9. Правила бизнес-логики

### 9.1. Регистрация

Система должна разрешать регистрацию только если `is_registration_open = true`.

Если регистрация закрыта, API должен вернуть ошибку.

### 9.2. Рекомендации

Рекомендации должны строиться только внутри одного мероприятия.

Участники из других мероприятий не должны попадать в список.

### 9.3. Контакты

Контактные данные являются приватной информацией.

Система не должна показывать контакты до принятия запроса.

### 9.4. Запросы

Система должна запрещать:

- запрос самому себе;
- запрос участнику из другого мероприятия;
- повторный активный запрос;
- принятие несуществующего запроса.

### 9.5. Match

Для MVP match появляется после принятия запроса.

В будущих версиях можно сделать модель взаимных лайков, где match создается только если оба участника отправили интерес друг другу.

## 11. MVP Scope

### 11.1. Входит в MVP

В MVP входит:

- создание мероприятия;
- регистрация участников;
- хранение профилей;
- рекомендации по тегам;
- отправка запросов;
- принятие запросов;
- открытие контактов после match;
- закрытие регистрации.

### 11.2. Не входит в MVP

В MVP не входит:

- сложная авторизация;
- платежи;
- полноценный чат;
- мобильное приложение;
- push-уведомления;
- сложная аналитика;
- интеграция с внешними календарями;
- модерация профилей;
- многоуровневая система ролей.

### 11.3. Возможные улучшения после MVP

После MVP можно добавить:

- QR-код для мероприятия;
- авторизацию через Telegram или email;
- личный кабинет организатора;
- аналитику активности;
- рейтинг рекомендаций;
- фильтры по целям знакомства;
- экспорт контактов;
- встроенный чат;
- AI-рекомендации.

## 12. Критерии готовности

### 12.1. Backend считается готовым, если:

- сервер запускается без ошибок;
- `/health` возвращает статус `ok`;
- можно создать мероприятие;
- можно добавить участника;
- можно получить рекомендации;
- можно отправить запрос;
- можно принять запрос;
- контакты открываются только после принятия запроса.

### 12.2. MVP считается готовым, если:

- пользователь может пройти основной сценарий без ручного вмешательства разработчика;
- данные сохраняются в базе;
- API можно протестировать через Swagger;
- нет критических ошибок в базовом flow.

### 12.3. Демо считается готовым, если:

- есть заранее подготовленное мероприятие;
- есть несколько тестовых участников;
- рекомендации выглядят логично;
- можно показать процесс match;
- можно объяснить ценность продукта за 1–2 минуты.

---

## 13. Пример пользовательского сценария

### 13.1. Организатор

1. Организатор открывает страницу создания мероприятия.
2. Вводит название: `PROD Hackathon Minsk`.
3. Добавляет описание.
4. Указывает теги: `Python`, `AI`, `Design`, `Startups`.
5. Получает ссылку или QR-код.
6. Показывает QR-код участникам.

### 13.2. Участник

1. Участник сканирует QR-код.
2. Заполняет имя, описание и интересы.
3. Попадает в список участников.
4. Открывает рекомендации.
5. Видит людей с похожими тегами.
6. Отправляет запрос.
7. Получает match.
8. Видит контакт другого участника.

---

## 14. Заключение

MeetPoint MVP должен быть сфокусирован на одной главной ценности: быстро помогать участникам мероприятия находить полезные знакомства.

Главный принцип продукта:

> Меньше случайных разговоров — больше осознанного нетворкинга.

Этот RFC описывает минимальную, но полноценную версию приложения, которую можно реализовать в рамках хакатона и показать на демо.
